## 2024-05-06 - In-Memory IP-Based Rate Limiting for Computational Endpoints
**Vulnerability:** Application-Layer Denial of Service (DoS) due to unbounded access to computationally expensive numerical root-finding endpoints.
**Learning:** When adding rate-limiting to mitigate this, avoid adding unapproved external dependencies (like `flask-limiter`). Instead, it is feasible to implement a lightweight, in-memory IP-based rate limiter using standard Python built-ins like `time.time()` and `collections.defaultdict` inside a `@before_request` hook. This provides a functional defense against basic script-based DoS without architectural overhead.
**Prevention:** Consider computational limits and rate limiting for any endpoint that executes mathematical root finders or heavy numerical algorithms. Default to zero-dependency solutions for minor security enhancements unless instructed otherwise.

## 2026-05-07 - Rate Limiter IP Spoofing & Global DoS Risk via Reverse Proxies
**Vulnerability:** The in-memory rate limiter relied directly on `request.remote_addr`, which resolves to the reverse proxy's IP (e.g., Vercel) instead of the actual client IP. This causes two critical issues: 1) Every user shares the same rate limit, causing a self-inflicted global DoS. 2) Attackers can bypass limits entirely by spoofing the `X-Forwarded-For` header if the proxy chain is not explicitly configured.
**Learning:** In Flask/Werkzeug environments deployed behind reverse proxies, `request.remote_addr` is inherently untrustworthy. Security controls relying on IP addresses must explicitly handle proxy headers, but doing so manually is error-prone.
**Prevention:** Always wrap the Flask application with `werkzeug.middleware.proxy_fix.ProxyFix` with the correct proxy count parameters (e.g., `x_for=1` for a single upstream proxy) to safely and natively resolve the real client IP.
